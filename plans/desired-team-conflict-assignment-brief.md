# 희망 팀 충돌 경고와 종료 후 팀 배정 기획서

작성일: 2026-06-30.

## 목적

경매 중 입찰 대상 선수의 희망 팀 정보와 입찰 팀 로스터의 기존 선수 희망 팀 정보가 충돌할 때, 해당 팀장에게 의사결정에 필요한 경고를 표시한다.

경매가 모두 끝난 뒤에는 각 로스터가 실제 몇 팀으로 배정될 수 있는지 경우의 수를 보여주고, 주최자가 최종 배정을 선택할 수 있는 화면을 제공한다.

## 현재 전제

- 경매 생성 시 선수 엑셀에는 희망 팀 정보가 포함될 수 있다.
- 현재 코드에는 선수 단위 `desired_team` 문자열 필드가 있고, 공개 입찰 대상 카드와 비공개 입찰 대상 카드에서 이미 표시된다.
- 희망 팀이 비어 있거나 `상관없음`인 선수는 모든 실제 팀 배정이 가능하다고 본다.
- 희망 팀 값은 `1팀`, `5팀`처럼 실제 배정 가능한 팀 번호를 가리킨다.
- 한 선수는 여러 희망 팀을 가질 수 있다.
- 한 로스터는 경매 중 임시로 구성된 팀이며, 경매 종료 후 실제 일정 진행 팀 번호로 다시 배정될 수 있다.
- 경매 중 낙찰은 유지하고, 희망 팀 충돌은 입찰 제한이 아니라 경고와 판단 보조 정보로만 사용한다.
- 경매 종료 후 실제 팀 배정은 주최자의 선택으로 확정한다.
- 희망 팀 입력은 현재 숫자 팀 기준으로 유지한다.
- 종료 후 팀 배정 결과는 일정 생성 전에 반드시 확정해야 한다.
- 희망 팀 조건은 선수 개인별 개별 만족이 아니라, 선수가 포함된 경매 팀 로스터 전체가 하나의 실제 팀 배정으로 함께 만족해야 하는 조건으로 본다.

## 용어

| 용어 | 의미 |
|---|---|
| 경매 팀 | 경매 중 입찰과 포인트를 보유하는 팀이다. 예를 들면 2번 팀장 로스터다. |
| 실제 팀 | 일정 진행에 쓰이는 최종 팀 번호다. 예를 들면 1팀, 5팀, 8팀이다. |
| 희망 팀 | 선수가 최종 배정받기를 희망하는 실제 팀 목록이다. |
| 상관없음 | 선수가 어떤 실제 팀으로 배정되어도 가능한 상태다. |
| 충돌 | 같은 경매 팀 로스터 안에서 선수들의 희망 팀 교집합이 사라지거나 줄어드는 상태다. |
| 후보 팀 | 특정 경매 팀 로스터 전체가 현재 희망 팀 조건을 만족하며 배정될 수 있는 실제 팀 목록이다. |

## 경매 중 충돌 경고

### 판단 시점

- 다음 경매 선수가 추첨되어 입찰 대상 정보에 표시된 직후 판단한다.
- 팀장이 입찰 버튼을 보기 전부터 판단 결과를 확인할 수 있어야 한다.
- 각 팀장 화면은 자기 팀 로스터와 현재 입찰 대상 선수를 기준으로만 경고를 본다.
- 주최자 화면은 전체 팀의 충돌 상태를 요약해서 볼 수 있으면 좋지만, 1차 범위에서는 팀장 경고를 우선한다.

### 판단 방식

1. 현재 팀 로스터에 포함된 각 선수의 희망 팀 목록을 구한다.
2. 희망 팀이 없는 선수 또는 `상관없음` 선수는 교집합 계산에서 제한 조건으로 사용하지 않는다.
3. 현재 입찰 대상 선수의 희망 팀 목록을 구한다.
4. 기존 로스터의 가능한 후보 팀과 입찰 대상 선수의 희망 팀 교집합을 계산한다.
5. 교집합이 비어 있으면 강한 충돌로 표시한다.
6. 교집합이 비어 있지는 않지만 기존 후보가 줄어들면 주의로 표시한다.
7. 입찰 대상 선수가 `상관없음`이면 충돌 없음으로 표시한다.

### 예시

현재 2번 팀 로스터에 A 선수가 있고 A 선수의 희망 팀이 `2팀`, `5팀`이라고 가정한다.

다음 경매 대상으로 B 선수가 추첨되었고 B 선수의 희망 팀이 `1팀`, `3팀`이면, 2번 팀 로스터의 기존 후보는 `2팀`, `5팀`이고 B 선수 후보는 `1팀`, `3팀`이다.

교집합이 없으므로 2번 팀장 화면에는 강한 충돌 경고를 표시한다.

표시 문구 초안은 아래와 같다.

```text
현재 로스터의 희망 팀과 입찰 대상 선수의 희망 팀이 겹치지 않습니다.
이 선수를 낙찰받으면 경매 종료 후 이 로스터는 희망 팀 조건을 만족하는 최종 팀 배정을 받지 못할 수 있습니다.
```

### 표시 강도

| 상태 | 조건 | UI 방향 |
|---|---|---|
| 충돌 없음 | 후보 팀이 유지된다. | 별도 경고 없음 또는 작은 `희망 팀 조건 충족` 표시다. |
| 주의 | 후보 팀이 줄어든다. | 노란색 계열 안내와 남은 후보 팀 표시다. |
| 강한 충돌 | 후보 팀 교집합이 없다. | 빨간색 또는 고대비 Cyber-Pixel 경고 효과와 명확한 문구다. |

## 경매 종료 후 팀 배정 화면

### 진입 조건

- 모든 경매가 종료되어 각 경매 팀 로스터가 확정된 뒤 표시한다.
- 로스터별 최소 인원과 최대 인원 조건을 만족해야 한다.
- 유찰 또는 미배정 선수가 남아 있으면 팀 배정 화면으로 넘어가기 전 별도 정리가 필요하다.

### 화면 목표

- 주최자가 각 경매 팀을 실제 팀 번호에 배정한다.
- 각 경매 팀의 가능한 실제 팀 후보를 즉시 볼 수 있다.
- 한 실제 팀은 하나의 경매 팀에만 배정된다.
- 주최자가 하나를 선택하면 다른 경매 팀의 후보에서 해당 실제 팀이 제거된다.
- 후보가 한 개만 남은 경매 팀은 자동 배정될 수 있다.
- 자동 배정은 즉시 확정하지 않고 제안 상태로 유지한다.
- 자동 배정 제안 결과도 주최자가 이해할 수 있도록 근거를 표시한다.
- 후보가 없는 로스터도 우선은 주최자가 예외 배정할 수 있게 한다.

## 종료 후 배정 규칙

### 후보 계산

- 경매 팀 로스터의 모든 선수에 대해 희망 팀 제한을 모은다.
- `상관없음` 선수는 제한 조건에서 제외한다.
- 제한 조건이 하나도 없으면 모든 실제 팀을 후보로 둔다.
- 제한 조건이 있으면 선수별 희망 팀 목록의 교집합을 후보로 둔다.
- 이 교집합은 로스터 전체가 같은 실제 팀 하나로 배정될 수 있는지를 판단하는 기준이다.
- 후보가 비어 있으면 해당 경매 팀은 현재 희망 팀 조건만으로 배정 불가 상태다.

### 선택 전파

1. 주최자가 한 경매 팀에 실제 팀을 선택한다.
2. 선택된 실제 팀은 미배정 경매 팀의 후보에서 제거된다.
3. 후보가 한 개만 남은 경매 팀은 자동 배정 제안 대상이 된다.
4. 자동 배정 제안은 즉시 확정하지 않고 주최자 승인 대기 상태로 유지한다.
5. 후보가 0개가 되는 팀이 생기면 현재 선택 조합은 막힌 상태로 표시한다.
6. 후보가 0개인 팀도 주최자가 예외 배정할 수 있지만, 예외 배정임을 명확히 표시한다.

### 자동 배정 제안 기준

- 자동 배정 제안은 후보가 정확히 한 개만 남았을 때 가능하다.
- 자동 배정 제안 전에 이미 주최자가 수동으로 고정한 선택은 유지한다.
- 자동 배정 제안 항목은 `자동 배정 제안` 표시를 붙이고, 주최자가 승인하거나 다른 선택으로 바꿀 수 있게 한다.
- 자동 배정 제안이 여러 개 연쇄적으로 발생하면 적용 순서와 이유를 로그처럼 보여준다.
- 제안 상태는 최종 배정 확정 전까지 실제 확정값으로 저장하지 않는다.

## 8팀 예시

경매 종료 후 8개 경매 팀 로스터가 아래 조건을 가진다고 가정한다.

| 경매 팀 | 희망 팀 조건 |
|---|---|
| A팀 | 상관없음 |
| B팀 | 상관없음 |
| C팀 | 1팀, 5팀, 6팀 |
| D팀 | 1팀, 2팀 |
| E팀 | 5팀, 8팀 |
| F팀 | 상관없음 |
| G팀 | 4팀, 7팀 |
| H팀 | 3팀, 4팀, 6팀 |

초기 후보는 아래와 같다.

| 경매 팀 | 초기 후보 |
|---|---|
| A팀 | 1팀, 2팀, 3팀, 4팀, 5팀, 6팀, 7팀, 8팀 |
| B팀 | 1팀, 2팀, 3팀, 4팀, 5팀, 6팀, 7팀, 8팀 |
| C팀 | 1팀, 5팀, 6팀 |
| D팀 | 1팀, 2팀 |
| E팀 | 5팀, 8팀 |
| F팀 | 1팀, 2팀, 3팀, 4팀, 5팀, 6팀, 7팀, 8팀 |
| G팀 | 4팀, 7팀 |
| H팀 | 3팀, 4팀, 6팀 |

C팀과 D팀은 `1팀` 후보가 겹친다.

주최자가 C팀을 `1팀`으로 선택하면 D팀의 후보에서 `1팀`이 제거되어 D팀은 `2팀`만 남는다.

이때 D팀은 자동 배정 제안 대상이 되고, 시스템은 D팀 `2팀` 배정을 제안 상태로 표시한다.

반대로 주최자가 D팀을 `1팀`으로 선택하면 C팀의 후보에서 `1팀`이 제거되어 C팀은 `5팀`, `6팀`만 남는다.

이 경우 C팀은 후보가 두 개이므로 자동 배정하지 않고 주최자 선택을 기다린다.

## 사용자 흐름

### 경매 중 팀장 흐름

1. 주최자가 다음 경매 선수를 추첨한다.
2. 팀장 화면에 입찰 대상 선수 정보와 희망 팀 정보가 표시된다.
3. 시스템이 팀장 자신의 현재 로스터와 입찰 대상 선수의 희망 팀 충돌을 계산한다.
4. 충돌이 있으면 입찰 버튼 근처 또는 입찰 대상 카드 하단에 경고를 표시한다.
5. 팀장은 경고를 보고도 입찰할 수 있다.
6. 낙찰 후 해당 팀 로스터의 남은 최종 배정 후보가 갱신된다.

### 경매 종료 후 주최자 흐름

1. 모든 로스터가 확정된다.
2. 주최자는 팀 배정 화면으로 이동한다.
3. 화면은 각 경매 팀의 후보 실제 팀과 배정 가능 여부를 보여준다.
4. 주최자가 한 팀의 실제 팀을 선택한다.
5. 시스템은 다른 팀의 후보를 갱신하고 자동 배정 가능 항목을 제안 상태로 표시한다.
6. 모든 경매 팀이 하나의 실제 팀에 배정되면 주최자가 최종 확정한다.
7. 확정 결과는 일정 생성 전에 반드시 저장되어야 한다.
8. 일정 생성과 일정 진행 단계는 확정된 팀 배정 결과를 사용한다.

## 데이터 요구사항

### 기존 데이터

- `players.desired_team`은 표시용 원본 문자열로 유지한다.
- 기존 엑셀 업로드의 희망 팀 열은 계속 지원한다.

### 추가로 필요한 해석 규칙

- `1팀, 5팀, 6팀`, `1팀/5팀/6팀`, `1 5 6`처럼 사용자가 입력할 수 있는 구분자를 정규화해야 한다.
- `상관없음`, `무관`, 빈 문자열은 제한 없음으로 해석한다.
- 팀 번호는 방의 팀 개수 범위를 벗어나면 검증 오류 또는 미인식 값으로 처리해야 한다.
- 팀명 입력은 현재 범위에서 지원하지 않는다.
- 원본 문자열과 정규화된 후보 목록을 분리하면 화면 표시와 계산 안정성을 함께 얻을 수 있다.

### 저장 후보

아래 저장 방식은 구현 시 선택이 필요하다.

| 방식 | 장점 | 단점 |
|---|---|---|
| `desired_team` 문자열만 유지하고 계산 시 파싱 | 마이그레이션이 작다. | 매번 파싱이 필요하고 입력 오류 처리가 늦다. |
| `desired_team`과 `desired_team_ids`를 함께 저장 | 계산이 안정적이다. | 생성 로직과 기존 데이터 보정이 필요하다. |
| 별도 배정 상태 문서를 둔다. | 종료 후 배정 흐름을 독립적으로 관리하기 좋다. | 경매 종료 계약과 문서가 늘어난다. |

초기 구현은 `desired_team` 원본을 유지하면서 공통 파서로 `desired_team_ids` 파생값을 계산하는 방식이 가장 작다.

## 확정 정책

- 희망 팀 충돌은 입찰 차단이 아니라 경고만 표시한다.
- 자동 배정은 즉시 적용하지 않고 주최자 승인 전 제안 상태로 유지한다.
- 후보가 없는 로스터도 우선은 주최자가 예외 배정할 수 있게 한다.
- 희망 팀 입력은 현재 숫자 팀만 허용한다.
- 종료 후 팀 배정 결과는 일정 생성 전에 반드시 확정해야 한다.
- 희망 팀 조건은 선수가 포함된 경매 팀 로스터 전체 만족 조건으로 진행한다.
- `상관없음` 선수가 많아 후보가 넓은 팀의 자동 배정 제안은 제한이 있는 팀의 모든 배정이 종료된 이후 갱신한다.
- 예외 배정 경고 문구는 상황별 1차 표시 문구를 사용한다.

## 예외 배정 경고 문구

예외 배정은 희망 팀 조건만으로는 정상 후보를 만들 수 없거나, 주최자가 운영상 배정을 강제로 확정해야 하는 상황을 말한다.

| 상황 | 예시 | 1차 표시 문구 |
|---|---|---|
| 로스터 전체 후보 없음 | 한 로스터에 `1팀, 2팀` 희망 선수와 `3팀, 4팀` 희망 선수가 함께 있어 교집합이 없다. | `희망 팀 조건을 만족하는 배정 후보가 없습니다. 예외 배정이 필요합니다.` |
| 선택 전파 후 후보 소진 | C팀을 `1팀`으로 확정한 뒤 D팀 후보 `1팀`이 제거되어 남은 후보가 없다. | `다른 팀 배정으로 인해 이 로스터의 희망 팀 후보가 모두 소진되었습니다.` |
| 숫자 팀 입력 오류 또는 범위 밖 값 | 희망 팀에 `9팀`이 입력됐지만 방은 8팀까지만 존재한다. | `인식할 수 없는 희망 팀 값이 있어 예외 배정 검토가 필요합니다.` |
| 운영상 강제 배정 | 후보는 남아 있지만 일정 운영 사유로 주최자가 다른 실제 팀에 배정한다. | `희망 팀 후보와 다른 팀으로 예외 배정되었습니다.` |

최종 결과 화면과 기록에는 예외 배정 여부, 원래 후보, 실제 확정 팀, 예외 사유를 함께 남긴다.

## 1차 구현 범위 제안

1. 희망 팀 문자열 정규화 유틸을 만든다.
2. 로스터와 입찰 대상 선수의 후보 교집합을 계산하는 순수 함수를 만든다.
3. 공개 입찰과 비공개 입찰 대상 카드 주변에 팀장 전용 충돌 경고를 표시한다.
4. 경매 종료 후 주최자 전용 팀 배정 화면 초안을 만든다.
5. 선택 전파와 단일 후보 자동 배정 제안 규칙을 순수 함수로 검증한다.
6. 실제 확정 저장은 화면 동작이 확정된 뒤 별도 단계로 진행한다.
7. 제한이 있는 팀의 모든 배정이 끝난 뒤 `상관없음` 중심 팀의 자동 배정 제안을 갱신한다.

## 검증 기준 초안

- A 선수 희망 팀이 `2팀, 5팀`이고 B 선수 희망 팀이 `1팀, 3팀`이면 2번 팀장 화면에 강한 충돌 경고가 표시된다.
- 기존 후보가 `1팀, 5팀, 6팀`이고 입찰 대상 후보가 `1팀, 6팀`이면 주의가 아니라 충돌 없음 또는 후보 축소 안내로 표시된다.
- 경매 종료 후 C팀을 `1팀`으로 선택하면 D팀의 후보가 `2팀`만 남고 자동 배정 제안 대상이 된다.
- 후보가 0개가 되는 선택은 최종 확정 전에 막힌 상태로 표시된다.
- 후보가 0개인 로스터도 주최자 예외 배정으로 진행할 수 있다.
- `상관없음` 팀은 아직 선택되지 않은 실제 팀 전체를 후보로 유지한다.
- 같은 로스터 안의 제한 있는 선수들은 모두 같은 실제 팀 후보 교집합을 기준으로 판정한다.
- 제한이 있는 팀의 모든 배정이 종료된 이후 `상관없음` 중심 팀의 자동 배정 제안이 갱신된다.
- 예외 배정이 발생하면 원래 후보, 실제 확정 팀, 예외 사유가 최종 기록에 남는다.
- 예외 배정 상황별 1차 표시 문구가 최종 결과 화면과 기록에 사용된다.
